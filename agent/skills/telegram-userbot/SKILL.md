# telegram-userbot

Доступ к **личному Telegram-аккаунту владельца** (Telethon, MTProto) — отдельный аккаунт-человек,
НЕ бот, через которого ты сейчас общаешься. Всё делается ТОБОЙ прямо в этом чате: настройку ты
проводишь сам (через `bash`-тул на хосте), а работу — через MCP-тулы
`connection__telegram-userbot__<tool>` (ищи их через `connection_search`).
**Пользователь только пишет в чат — терминал он не трогает.**

## ⚠️ Сначала — предупреди и получи согласие
Автоматизация личного аккаунта нарушает ToS Telegram и может привести к **бану аккаунта**
(особенно отправка). Одной фразой скажи владельцу, что это на его страх и риск и что безопаснее
всего только чтение. Продолжай, только если он согласился.

## Шаг 1. Подключён ли аккаунт?
Вызови `login_status`.
- `connected` → всё готово, переходи к работе (Шаг 4).
- `not_connected` → нужен онбординг (Шаг 3), но сперва проверь, поднят ли прокси (Шаг 2).
- Если сам вызов падает (сервер недоступен) → прокси ещё не установлен, иди в Шаг 2.

## Шаг 2. Проверить прокси и учётные данные
Прокси поднимает администратор сервера. Сначала вызови `login_status`.

- Если вызов доступен и вернул `not_connected`, **не проси api_id/api_hash**: они уже сохранены на сервере. Сразу переходи к QR-входу (Шаг 3).
- Если вызов недоступен, попроси администратора запустить `iva userbot setup`. API-данные запрашивай у владельца только когда администратор явно подтвердил, что их нет в `.env`.
- Никогда не проси владельца повторно присылать существующие API-ключи и не показывай их в чате.

## Шаг 3. Онбординг по QR (в чате)
1. Вызови `qr_login_start`. Сервер отрисует QR и **сам пришлёт его картинкой в этот чат**.
   (Если сразу после setup вызов не прошёл — прокси ещё поднимается, повтори через несколько секунд.)
2. Скажи владельцу: открой приложение Telegram **того аккаунта, который подключаешь** →
   Настройки → Устройства → Подключить устройство → отсканируй QR.
3. Опрашивай `qr_login_status` раз в несколько секунд:
   - `authorized` → готово.
   - `password_needed` → включена двухфакторка. Попроси у владельца пароль и передай в
     `qr_login_password`. **Предупреди:** пароль пройдёт через чат — пусть сменит его потом, если
     переживает. Не логируй и не повторяй пароль в ответах.
   - `waiting` → ещё не отсканировал, подожди.
   - `expired` / `error` → начни заново с `qr_login_start`, объясни причину.

Сессия хранится на сервере — повторный онбординг после рестарта не нужен.

## Шаг 4. Работа с аккаунтом
Подключение жёстко **read-only**. Инструменты отправки, изменения профиля, контактов и глобального поиска удалены на сервере.

1. Пока включён режим выбора, допустим только список чатов (без текста сообщений). Покажи владельцу названия и ID, затем дождись его явного выбора.
2. Администратор добавляет выбранные ID в серверный allowlist. До этого любые чтение истории, поиск и медиа должны возвращать отказ.
3. После включения allowlist работай только с разрешённым `chat_id`: `get_history`, `list_messages`, `get_messages`, `get_message_context`, `search_messages` и метаданные сообщений.
4. Никогда не читай чаты, не вошедшие в allowlist, и не пытайся обойти это ограничение.
5. Для MCP-тулов не передавай пустое поле `account`. Оставляй его отсутствующим; если инструмент требует его явно, используй только `default`.
6. При ошибке MCP не запускай рекурсивный `grep`/`find` по проекту и не пытайся искать внутренние скрипты сервера. Сообщи краткую ошибку владельцу и остановись.

## Безопасный обзор чатов
Когда владелец просит обзор или пополнение памяти по чатам:
1. Обрабатывай за один запуск не более **двух ID**, прямо названных владельцем. Не пытайся обойти весь allowlist и не запрашивай список остальных чатов.
2. Для каждого чата читай не более **30 последних сообщений** за один вызов. Не делай пагинацию и не запрашивай полную историю в рамках того же запуска.
3. Верни максимум пять коротких пунктов на чат: темы, решения, задачи, риски, изменения. Если владелец явно просил сохранить память, запиши только эти устойчивые факты в карточку; не копируй сырой текст переписки.
4. После двух чатов остановись и предложи следующий пакет. При ошибке одного чата не ретраишь его и не начинай обход сервера: сообщи ID и краткую ошибку.
5. Для обзора всей выборки работай пакетами по два чата. Никогда не объединяй содержимое разных чатов в одну большую выборку модели.
## Анти-бан — обязательно
Сервер уже принудительно соблюдает FloodWait и притормаживает отправки, но лимиты Telegram —
на уровне аккаунта. **Перед любой отправкой прочитай `safety.md` в этом скилле** и следуй ему:
рандомные паузы, не бомбить, не слать одинаковый текст веером, стоп при `PeerFlood`. Чтение почти
не банится — предпочитай его. Сомневаешься в отправке — замедлись или спроси владельца.
